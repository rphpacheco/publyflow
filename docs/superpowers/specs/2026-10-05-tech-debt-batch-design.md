## 1. Lazy AI clients
- **Problem:** `src/lib/ai/index.ts` builds the Jev and OpenAI clients at module load (`process.env.OPENAI_API_KEY!`); without the key, importing the inbox message route throws before any handling.
- **Change:** `ai` creates each provider client on first use. Missing `JEV_API_KEY` → the composite classifier skips Jev and uses OpenAI. Missing `OPENAI_API_KEY` → a new `AiNotConfiguredError` (in `src/lib/ai`), which the inbox ingest surfaces; `POST /api/inbox/messages` maps it to **503** `{ error: "A classificação por IA não está configurada neste ambiente.", code: "AI_NOT_CONFIGURED" }`. The existing 502 for real classification failures is unchanged.
- **Tests:** importing `@/lib/ai` with no keys does not throw; the route returns 503 with no OpenAI key; with only an OpenAI key the composite classifies via OpenAI without calling Jev.

## 3. Explicit company/brand ids on inbox conversion
- **Problem:** `resolvePartyIdFromGuess` returns an explicit `input.companyId` / `input.brandId` unchecked (`src/services/commercial-inquiry.service.ts`), so another org's id could be linked.
- **Change:** an explicit id must exist in the organization; otherwise the conversion throws before inserting anything. Route maps to **422** `{ error: "Empresa selecionada não encontrada.", code: "COMPANY_NOT_FOUND" }` / `{ error: "Marca selecionada não encontrada.", code: "BRAND_NOT_FOUND" }` (in the inquiry error mapper `src/app/api/commercial-inquiries/[id]/inquiry-errors.ts`).
- **Tests:** foreign-org company id and brand id → 422 and no contact/lead/opportunity created; unknown id → 422; own-org id still works.

## 4. Reopening a responded proposal requires server-side confirmation
- **Context:** concurrent publishes are already safe (row lock + idempotent re-send of the same version). The open gap: publishing a new version of a proposal the client already **accepted or rejected** reopens the round, and that confirmation exists only in the UI.
- **Change:** `ProposalSendingService.publish(..., { withoutApproval?, reopen? })`. When the proposal status is `APPROVED` or `REJECTED` and the call would create a new publication (i.e. not the idempotent no-op), it requires `reopen: true`; otherwise it throws `ReopenRequiredError` (proposals domain errors). `POST /api/proposals/[id]/publications` reads `reopen` from the body (`body?.reopen === true`) and maps the error to **409** `{ error: "Esta proposta já foi respondida pelo cliente. Confirme para abrir uma nova rodada.", code: "REOPEN_REQUIRED" }`.
- **UI (`src/components/proposals/proposal-send-panel.tsx`):** the existing "Reenviar abre uma nova rodada…" confirmation sends `reopen: true` (also combined with `withoutApproval`). If a publish returns 409 `REOPEN_REQUIRED` (stale page), the panel opens that same confirmation instead of showing an error toast.
- **Tests:** service — APPROVED/REJECTED + new version without `reopen` → `ReopenRequiredError`; with `reopen` → publishes and status becomes SENT; idempotent re-send of the already-published version needs no `reopen`; DRAFT/SENT/CHANGES_REQUESTED unaffected. Route 409 body. Panel — confirm sends `reopen: true`; a 409 `REOPEN_REQUIRED` opens the confirmation.
